# Установка и настройка Forest Keeper на своём ПК

[К содержанию](README.md) · [Проверочный сценарий](walkthrough-checklist.md) · [Если ошибка](troubleshooting.md)

## 0. Выберите правильный вариант
**Рекомендуемый:** Windows 10/11 с WSL2 Ubuntu + Docker Desktop. На Linux нужен Docker Engine с Compose plugin. На macOS — Docker Desktop + терминал Bash. Все команды ниже выполняйте **в терминале Ubuntu/WSL2 или Bash**, не в PowerShell. Если на Windows нет WSL2, сперва установите его по инструкции Microsoft, перезагрузите ПК и запустите Ubuntu. Для обычного теста GPU не нужен.

Ориентировочный стартовый ресурс для **приложения без Qwen**: 4 логических CPU, 8 ГиБ RAM, 15 ГиБ свободного диска. Это плановая конфигурация, а не гарантированный измеренный минимум. Понадобится интернет для скачивания исходников и контейнеров. На компьютере должны быть **Git, Docker, Docker Compose v2, Bash, curl и OpenSSL**. Docker Desktop должен быть запущен.

Не переключайтесь на PR #33 для обычного теста: там экспериментальный Qwen, который ещё не принят.

## 1. Проверить окружение

В терминале Ubuntu/WSL или Bash:
```bash
git --version
docker --version
docker compose version
docker info
bash --version
openssl version
curl --version
```
Каждая команда должна отработать без ошибки. Если `docker info` сообщает, что daemon недоступен, запустите Docker Desktop и включите WSL integration для Ubuntu; либо настройте Docker Engine в Linux. Пока Docker не работает, дальше идти бессмысленно.

## 2. Получить проверяемую ветку

```bash
git clone --branch main https://github.com/SergeyRassohin/Forest-Keeper.git
cd Forest-Keeper
git status --short
git rev-parse HEAD
```

`git status --short` должен быть пустым. **Запишите полный SHA** из последней команды в свой чеклист. `main` может получать новые коммиты, поэтому дата документа не заменяет SHA.

Если папка `Forest-Keeper` уже существует, не выполняйте `clone` поверх неё: перейдите внутрь и проверьте `git status`, `git branch --show-current`, `git rev-parse HEAD`. Не делайте `git reset --hard` ради инструкции.

## 3. Первый запуск

Из корня репозитория:
```bash
bash scripts/dev-init.sh
docker compose up --build -d --wait --wait-timeout 180
docker compose ps -a
```

Инициализация создаёт локальный `.env` и dev TLS-сертификат в `deploy/local/tls/`. Это **секреты локального запуска**, их нельзя пересылать проверяющим или выкладывать в Git. При повторном вызове `dev-init.sh` существующие секреты сохраняются.

Ожидаем: `postgres`, `redis`, `backend`, `worker`, `frontend` активны; там, где настроен healthcheck, состояние `healthy`. Контейнер одноразовой миграции `migrate` со статусом **Exited (0)** — это нормально. Если иные контейнеры `Restarting`/`unhealthy`, откройте [разбор ошибок](troubleshooting.md), не стирайте БД.

Проверить доступность API:
```bash
curl --fail --retry 15 --retry-connrefused --retry-delay 1 --cacert deploy/local/tls/dev.crt https://localhost:8443/api/v1/health
```
Ожидается HTTP 200 и `status: ok`, включая проверку БД и Redis. **Это проверка инфраструктуры, не доказательство правильности бизнес-результатов.**

Откройте **https://localhost:8443** на **этом же компьютере**. Браузер может предупредить о самоподписанном **тестовом** сертификате: исключение допускается только для собственного localhost. Не отключайте TLS-проверку в системе. Сертификат имеет ограниченный срок действия (в исходном quickstart: 30 дней).

При работе на удалённом Linux-сервере используйте туннель:
```bash
ssh -L 8443:127.0.0.1:8443 user@server
```
И открывайте `https://localhost:8443` на своей машине. Для персонального теста предпочтителен локальный Docker.

## 4. Создать первый аккаунт

Выполните **один раз**, если пользователей ещё нет:
```bash
docker compose exec -T backend python -m app.auth.bootstrap --login admin --full-name "Администратор проверки"
```
Команда запросит **свой новый пароль 12–128 символов** (ввод скрыт). Готового пароля и общей тестовой учётной записи нет. Не помещайте пароль в команды, переписку или скриншоты.

Зайдите через браузер как `admin`. Администратор добавляет источники/пользователей и запускает импорт. **ADMIN не получает автоматически право принимать бизнес-решения.**

В разделе **«Пользователи»** создайте `reviewer` с ролью **REVIEWER** и отдельным паролем. Для REVIEWER явно предоставьте доступ к используемому учебному домену через настройку **«Область данных»** (при личном испытании допустим учебный полный scope). Без scope экран конфликтов может быть пустым даже при существующих данных. Изменения пользователей/доступов требуют свежего входа ADMIN: если операция отклонена, выйдите и войдите снова.

Дополнительно можно создать `viewer` с ролью VIEWER для проверки ограничений.

## 5. Проверка настройки

- [ ] Главная страница открывается по `https://localhost:8443`.
- [ ] Health показывает OK.
- [ ] Вход ADMIN работает.
- [ ] Создан REVIEWER и предоставлен учебный scope.
- [ ] Записан SHA проверяемой версии.
- [ ] Файлы `.env` и TLS-ключи не отправлены никому.
- [ ] Можно перейти к [сценарию](walkthrough-checklist.md).

## 6. Как безопасно выключать и запускать

Для обычной остановки **без удаления данных**:
```bash
docker compose stop -t 30 worker
docker compose down
```

Для повторного запуска:
```bash
docker compose up -d --wait --wait-timeout 180
```

Для теста восстановления после перезапуска:
```bash
docker compose stop -t 30 worker
docker compose restart postgres redis backend frontend
docker compose up -d --wait --wait-timeout 180 worker
```

**Никогда не используйте `docker compose down -v` для восстановления**: ключ `-v` удаляет volumes, включая данные БД. Не удаляйте `.env`, `deploy/local/tls/` и локальные volumes во время сценария. Любое обновление/переустановка перед сохранением ценных данных требует резервной копии (отдельная процедура поставки/backup не является готовым промышленным Update Service).
