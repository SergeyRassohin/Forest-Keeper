# Руководство пользователя Forest Keeper

[К содержанию](README.md) · [Установка](installation.md) · [Проверочный сценарий](walkthrough-checklist.md)

## Что делает продукт
Forest Keeper сравнивает выгрузки из разных источников, хранит неизменённые исходные данные и их происхождение, нормализует значения по **заданным профилям**, сопоставляет записи, показывает различия и даёт человеку подтвердить бизнес-решение. **Источники не изменяются**: никакой записи обратно в 1С/Excel.

Работайте в браузере: `https://localhost:8443`. Перед первым входом пройдите [установку](installation.md).

## Пользователи и права
- **ADMIN**: настройка пользователей и источников, запуск технических операций; это не роль бизнес-эксперта.
- **REVIEWER**: ручная проверка спорных сопоставлений и принятие решений в разрешённой области данных.
- **VIEWER**: просмотр доступных данных без принятия решений.
- **Scope**: права привязаны к домену данных; один лишь статус REVIEWER не означает доступ ко всему. Для учебного сценария ADMIN заранее предоставляет нужный scope.

## Главные разделы
**«Состояние сервера»**: проверка соединения/готовности. Зелёный health не обещает, что ваши данные нормализованы или Qwen доступен.

**«Импорт данных»**: создание источника FILE или ONE_C, загрузка CSV/XLSX/XML, просмотр ImportBatch, raw-записей, позиций и хеша оригинала. Сначала создайте источник, затем выберите файл. Поддержка формата **не гарантирует смыслового понимания любых колонок**. Для собственного нестандартного CSV/XML может понадобиться отдельный mapping profile.

**«Нормализация»** (внутри карточки импорта): выбор профиля и запуск. Для учебных материалов используйте **synthetic-material v1**, для примера землетрясений USGS — **public-earthquake v1**. Не применяйте профиль чужого домена. Следите за статусом COMPLETED; raw не подменяется нормализованным значением.

**«Сопоставление»**: выберите два успешных запуска нормализации одного совместимого профиля и начните matching. Просматривайте статусы «Совпадение», «Требует проверки», «Разные сущности». Сходство по тексту не означает автоматического подтверждения одной сущности. Если пара требует ручной проверки, REVIEWER записывает причину и подтверждает или отклоняет идентичность.

**«Конфликты»**: после анализа конфликтов откройте кейс; сравните источники, raw, normalized, единицы, основание (Basis), provenance и версии. Типы VALUE_MISMATCH и MISSING не означают, что система определила «правильное» значение.

**«Рассмотрение» / Human Review**: REVIEWER с нужным scope запускает рассмотрение конфликта, выбирает доступное действие (например, выбрать значение источника, указать значение, отложить или отметить недостаток данных), пишет основание, **проверяет итог перед сохранением**. Сохранение создаёт неизменяемый **Decision**. Повторное рассмотрение создаёт новую запись, старая не стирается. Действие не меняет файлы источника.

**Decision Registry**: история решений с ID, автором, временем, основанием и связанной историей. При конфликте двух одновременных сохранений возможен HTTP 409: перечитайте текущий кейс вместо бездумной повторной отправки.

**Похожие решения и рекомендации (Stage 7–8)**: в `main` код модулей есть, но **production embedding provider отключён**. В обычной конфигурации поиск может показывать UNAVAILABLE или abstain. Положительный synthetic demo режим требует специального изолированного test setup и не доказывает промышленное качество. Не ожидайте «AI предложил правильный вариант» в этом личном сценарии. Результат рекомендации не создаёт Decision автоматически.

**Локальный Qwen (Stage 9)**: **ещё не включён в `main`**; находится в draft PR #33 с незакрытыми performance/quality gates. Для теста основных функций не нужен.

**Тема интерфейса**: переключатель светлая/тёмная тема в общей шапке, на экране входа и рабочих страницах. Настройка сохраняется локально в браузере.

## На что смотреть при сравнении 1С и файла
1. Совпадает ли бизнес-ключ/идентичность записи, а не только похожее название?
2. Одинаковы ли единицы и смысл значений?
3. Какое именно исходное значение было в каждом источнике?
4. Есть ли доказательства, что пропуск означает отсутствие, а не ошибку парсинга?
5. На чём основан выбор человека? Сохраните понятную причину.
6. Не изменился ли scope/правило/контекст после открытия карточки?
