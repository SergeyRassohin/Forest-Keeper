# Forest Keeper — Object Lifecycles / State Models v0.1

Статус: обязательная спецификация жизненных циклов ключевых объектов MVP.

## 1. Назначение

Этот документ фиксирует для ключевых сущностей Forest Keeper:

- состояния объекта;
- допустимые переходы;
- событие или действие, вызывающее переход;
- ограничения на изменение объекта;
- связь переходов с Audit;
- правила, которые не должны трактоваться по-разному в backend, frontend и тестах.

Принцип: **статус объекта определяет допустимые действия над ним**.

Документ дополняет:
- `docs/development/mvp-development-plan-v0.1.md`;
- `docs/api/api-contract-v0.1.md`;
- `docs/workflows/workflows-v0.2.md`;
- `docs/decisions/decision-log.md`.

Если этот документ противоречит более новому явному решению в `decision-log.md`, приоритет имеет `decision-log.md`, а противоречие должно быть исправлено в документации.

---

## 2. Общие правила

1. Любой переход состояния, влияющий на бизнес-результат, фиксируется в Audit.
2. Нельзя удалять историю решений человека путём изменения старого Decision.
3. Recommendation не является Decision и не должна менять данные.
4. AI/LLM не имеет права самостоятельно менять статус Conflict на RESOLVED и не активирует Rule.
5. Повторная обработка одного и того же входа должна быть идемпотентной настолько, насколько это возможно.
6. RawRecord не редактируется после сохранения; исправления источника приходят новым импортом.
7. Каноническое представление служит сравнению и не является автоматическим источником истины.
8. Любое состояние UNKNOWN / неоднозначность маршрутизируется в Human Review, а не маскируется высоким AI confidence.

# 3. ImportBatch

## 3.1 Назначение

ImportBatch представляет одну загрузку файла или логически единого пакета данных из SourceSystem.

## 3.2 Состояния

| Статус | Смысл |
|---|---|
| CREATED | Пакет зарегистрирован, исходный файл принят, обработка ещё не началась |
| QUEUED | Задание поставлено в очередь фоновой обработки |
| PROCESSING | Выполняется чтение, разбор и создание RawRecord |
| COMPLETED | Обработка завершена без ошибок, блокирующих импорт |
| COMPLETED_WITH_ERRORS | Пакет обработан частично; ошибки отдельных записей сохранены |
| FAILED | Пакет не может быть обработан как единое целое |

## 3.3 Допустимые переходы

```text
CREATED → QUEUED → PROCESSING → COMPLETED
                         ├────→ COMPLETED_WITH_ERRORS
                         └────→ FAILED
```

Повторная попытка после FAILED не переписывает историю. Создаётся новая попытка обработки, связанная с исходным ImportBatch либо новый ImportBatch согласно реализации retry. В обоих случаях первая ошибка остаётся в Audit.

## 3.4 Ограничения

- исходный файл, checksum и provenance после регистрации не изменяются;
- RawRecord не удаляются из истории при частичных ошибках;
- COMPLETED_WITH_ERRORS не эквивалентен FAILED;
- повторная загрузка того же файла по checksum должна быть обнаруживаема.

# 4. RawRecord

## 4.1 Жизненный цикл

RawRecord является неизменяемым снимком исходной записи.

Состояние как бизнес workflow для RawRecord не требуется.

После создания допускается только добавление технических метаданных обработки, не изменяющих исходное значение.

## 4.2 Правило неизменяемости

```text
SOURCE VALUE → RawRecord
```

Нормализация создаёт производное представление и не переписывает RawRecord.

---

# 5. MatchCandidate

## 5.1 Назначение

MatchCandidate описывает гипотезу, что записи из разных источников относятся к одной бизнес-сущности.

## 5.2 Результат сопоставления

| Статус | Смысл |
|---|---|
| POSSIBLE_MATCH | Сходство есть, но автоматического подтверждения недостаточно |
| MATCHED | Сопоставление подтверждено правилами, порогом или человеком |
| NOT_MATCHED | Кандидат отклонён; записи считаются разными сущностями |

## 5.3 Допустимые переходы

```text
POSSIBLE_MATCH → MATCHED
POSSIBLE_MATCH → NOT_MATCHED
```

Автоматический matching может сразу создать результат MATCHED или NOT_MATCHED, если это допускают утверждённые пороги и правила.

## 5.4 Ограничения

- основание сопоставления и similarity/confidence сохраняются;
- embeddings не могут быть единственным необъяснимым основанием;
- изменение порогов не должно задним числом переписывать старые результаты без повторного анализа.

---

# 6. Conflict

## 6.1 Назначение

Conflict создаётся, когда FK обнаруживает расхождение, нарушение правила, отсутствие данных или иной случай, требующий объяснения или Human Review.

Типы MVP:
- VALUE_MISMATCH;
- DUPLICATE;
- FORMAT;
- MISSING.

## 6.2 Состояния

| Статус | Смысл |
|---|---|
| DETECTED | Конфликт обнаружен системой и ещё не взят на рассмотрение |
| IN_REVIEW | Конфликт открыт пользователем/назначен на Human Review |
| RESOLVED | Человек принял подтверждённое решение и создан Decision |
| REOPENED | Ранее решённый логический конфликт снова требует рассмотрения |

## 6.3 Основной переход

```text
DETECTED → IN_REVIEW → RESOLVED
                         ↓
                      Decision
```

REOPENED используется только если система связывает повторный случай с тем же логическим конфликтом:

```text
RESOLVED → REOPENED → IN_REVIEW → RESOLVED
```

Для MVP предпочтительный вариант при новом импорте: создавать **новый Conflict**, связанный с предыдущим через similarity / prior case reference. REOPENED оставлен для явного пересмотра того же случая.

## 6.4 Разрешённые действия

### DETECTED
- просмотр;
- построение recommendation;
- поиск похожих решений;
- перевод в IN_REVIEW.

### IN_REVIEW
- просмотр evidence;
- просмотр Recommendation;
- добавление комментария;
- принятие Human Decision.

### RESOLVED
- просмотр;
- просмотр Decision;
- просмотр Audit;
- изменение исходного Decision запрещено.

### REOPENED
- причины переоткрытия обязательны;
- прошлые Decisions остаются неизменными;
- новое решение создаёт новый Decision.

## 6.5 Условия RESOLVED

Conflict может стать RESOLVED только после успешного создания Decision.

Recommendation сама по себе Conflict не закрывает.

# 7. Recommendation

## 7.1 Назначение

Recommendation — вычисляемое предложение FK для текущего Conflict на основе:

- текущего конфликта;
- действующих Rules;
- CustomerTemplate;
- похожих подтверждённых Decisions;
- Authoritative Source, если задан;
- AI/LLM как объясняющего/аналитического компонента.

## 7.2 Состояния

| Статус | Смысл |
|---|---|
| GENERATING | Рекомендация рассчитывается |
| READY | Рекомендация доступна пользователю |
| STALE | Контекст изменился, старая рекомендация больше не считается актуальной |
| FAILED | Построение завершилось технической ошибкой |

## 7.3 Переходы

```text
GENERATING → READY
     └────→ FAILED

READY → STALE
```

Новый расчёт после STALE или FAILED создаёт новую версию Recommendation либо новый объект Recommendation.

## 7.4 Что делает Recommendation устаревшей

Recommendation должна стать STALE, если после её построения изменилось что-либо, влияющее на вывод:

- Conflict/context;
- Rules;
- CustomerTemplate;
- Authoritative Source;
- набор используемых похожих Decisions;
- алгоритм/модель в случае версионируемого расчёта.

## 7.5 Критическое правило

У Recommendation нет статуса ACCEPTED.

Нажатие пользователем «принять рекомендацию» создаёт **Decision**, после чего Conflict становится RESOLVED.

Это не даёт backend права превращать Recommendation в источник истины.

---

# 8. Decision

## 8.1 Назначение

Decision — подтверждённое решение человека по конкретному Conflict с сохранённым контекстом.

## 8.2 Жизненный цикл

Decision является **неизменяемым бизнес-событием**.

После создания он не редактируется и не удаляется обычным приложением.

```text
Human Review → Decision (immutable)
```

## 8.3 Исправление ошибочного решения

Если решение необходимо пересмотреть:

1. исходный Decision остаётся в истории;
2. Conflict переходит в REOPENED либо создаётся новый связанный Conflict;
3. создаётся новый Decision;
4. новый Decision содержит ссылку `supersedes_decision_id` или эквивалентную связь;
5. Audit хранит обе версии истории.

## 8.4 Обязательный контекст

Decision должен сохранять как минимум:

- conflict_id;
- actor/user_id;
- decision_type;
- выбранный результат;
- исходные значения;
- нормализованные значения, участвовавшие в рассмотрении;
- source/provenance;
- применённые Rules/Basis;
- использованную Recommendation, если была;
- comment/reason;
- timestamp;
- контекст, достаточный для последующего similarity retrieval.

# 9. Rule

## 9.1 Назначение

Rule — формальное, версионируемое правило клиента или базовое правило FK.

Origin:
- FK_DEFAULT;
- CUSTOMER;
- LEARNED_PROPOSAL.

## 9.2 Состояния

| Статус | Смысл |
|---|---|
| DRAFT | Правило создано/изменено, но не участвует в анализе |
| ACTIVE | Правило утверждено и применяется к новым анализам |
| INACTIVE | Правило отключено, но хранится для истории и воспроизводимости |

## 9.3 Переходы

```text
DRAFT → ACTIVE → INACTIVE
  ↑        │
  └────────┘  (через новую ревизию/версию)
```

Изменение содержания ACTIVE Rule не должно молча переписывать активную версию. Предпочтительно создавать новую версию/ревизию правила.

## 9.4 Ограничения

- AI не переводит Rule в ACTIVE;
- активировать Rule может только действие, разрешённое RBAC;
- изменение/активация/деактивация фиксируется в Audit;
- старые Decisions должны оставаться объяснимыми через версию правила, действовавшую в момент решения.

---

# 10. RuleSuggestion

## 10.1 Назначение

RuleSuggestion создаётся, когда FK обнаруживает устойчивый повторяющийся паттерн подтверждённых человеческих решений и предлагает формализовать его.

## 10.2 Состояния

| Статус | Смысл |
|---|---|
| PROPOSED | Предложение сформировано и ожидает человека |
| ACCEPTED | Человек согласился формализовать правило |
| REJECTED | Человек отклонил предложение |
| EXPIRED | Контекст предложения устарел до принятия решения |

## 10.3 Переходы

```text
PROPOSED → ACCEPTED
    ├────→ REJECTED
    └────→ EXPIRED
```

При ACCEPTED создаётся новая версия Rule или новое Rule. Включение его в ACTIVE должно пройти тот же контролируемый путь, что и для любого другого Rule.

Автоматическая активация без человека запрещена.

---

# 11. CustomerTemplate

## 11.1 Назначение

CustomerTemplate хранит конфигурацию структуры, mappings, обязательности и правил клиента.

## 11.2 Модель версий

Для MVP CustomerTemplate должен быть версионируемым.

Рекомендуемые состояния:

| Статус | Смысл |
|---|---|
| DRAFT | Изменяемая версия конфигурации |
| ACTIVE | Текущая применяемая версия |
| ARCHIVED | Предыдущая версия, сохранённая для воспроизводимости |

## 11.3 Переходы

```text
DRAFT → ACTIVE → ARCHIVED
```

При активации новой версии предыдущая ACTIVE становится ARCHIVED.

---

# 12. License

Жизненный цикл лицензии уже зафиксирован проектным решением:

```text
ACTIVE → GRACE_PERIOD → READ_ONLY
```

При READ_ONLY данные клиента, Audit, экспорт и функции администрирования/продления лицензии остаются доступны в рамках утверждённой лицензионной модели. Истечение лицензии не удаляет и не блокирует клиентские данные полностью.

---

# 13. AuditEvent

AuditEvent является append-only записью.

У него нет пользовательского lifecycle.

Запись AuditEvent:
- создаётся;
- не редактируется обычными пользователями;
- не удаляется в рамках штатной бизнес-логики.

Корректировка истории выполняется только новой записью AuditEvent.

---

# 14. Связь объектов в главном MVP-сценарии

```text
ImportBatch
  CREATED
    ↓
  QUEUED
    ↓
  PROCESSING
    ↓
  COMPLETED / COMPLETED_WITH_ERRORS
    ↓
RawRecord (immutable)
    ↓
Normalization
    ↓
MatchCandidate
    ↓
MATCHED / POSSIBLE_MATCH / NOT_MATCHED
    ↓
Conflict
DETECTED → IN_REVIEW
    ↓
Recommendation
GENERATING → READY
    ↓
Human Review
    ↓
Decision (immutable)
    ↓
Conflict RESOLVED
    ↓
Similarity retrieval for future cases
    ↓
RuleSuggestion PROPOSED
    ↓ human approval
Rule DRAFT / ACTIVE
```

# 15. Инварианты для реализации и тестов

1. Нельзя получить RESOLVED Conflict без Decision.
2. Нельзя изменить существующий Decision для исправления истории.
3. Нельзя считать Recommendation решением человека.
4. Нельзя активировать Rule только на основании AI/LLM output.
5. Нельзя переписать RawRecord нормализованным значением.
6. Нельзя скрыть ошибку отдельной записи переводом всего ImportBatch в COMPLETED без фиксации ошибки.
7. При изменении контекста READY Recommendation должна быть пересчитана или помечена STALE.
8. Новая версия Rule/CustomerTemplate не должна уничтожать старую версию, если она использовалась в ранее принятом Decision.
9. Любое значимое изменение статуса должно быть отражено в Audit.
10. E2E-тест MVP обязан проверять последовательность:
   `Import → Match → Conflict → Recommendation → Human Decision → Decision Registry → Similar future Recommendation`.

# 16. Что намеренно не фиксируется в v0.1

Отдельным документом Access Control Matrix должны быть зафиксированы точные права ролей:

- VIEWER;
- REVIEWER;
- DATA_OWNER;
- ADMIN.

Этот документ определяет **какие переходы допустимы**, но не подменяет матрицу прав, определяющую **кто именно** имеет право выполнить каждый переход.

Также пока не фиксируются:
- точные matching thresholds;
- SLA переходов/обработки;
- автоматическое назначение исполнителя;
- controlled publisher/write-back;
- production workflow beyond MVP.

Эти параметры должны задаваться отдельными требованиями или более поздними версиями спецификации.
