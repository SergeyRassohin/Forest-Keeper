## Canonical inventory and resolved specification differences

- Canonical outcomes remain SELECT_VALUE / ENTER_VALUE / INSUFFICIENT_DATA / DEFERRED. Source A/B are UI choices within SELECT_VALUE, not new enum values. No false-positive/not-actionable action exists in the canonical model, so none is invented.
- Conflict states remain OPEN / IN_REVIEW / RESOLVED / INSUFFICIENT_DATA. Reading a card never starts review. Explicit authenticated POST starts review, under conflict.review.start. DEFERRED preserves IN_REVIEW; insufficient data has its canonical state and immutable Decision. A correction of the same historical case explicitly enters IN_REVIEW and creates a superseding Decision; new source imports still create new Conflicts.
- Decision ACTIVE/SUPERSEDED is derived from the immutable successor relation, not a mutable status field. This resolves the lifecycle wording “becomes SUPERSEDED” without rewriting the original Decision. A unique first Decision and unique successor produce one linear history/effective head per Conflict.
- Current Stage5 conflicts are wholly protected by an append-only trigger. Migration0007 will permit only lifecycle/version/effective-pointer updates, retaining immutable source/evidence/Basis. Deferred database constraints require matching Decision/head/state at transaction commit. No backfilled fake Decisions.
- The older MVP plan split Human Review and Registry into stages6/7 and mentioned recommendations. The later explicit issue25 combines Human Review+Registry in Stage6 and excludes retrieval/recommendation/AI/write-back; it is authoritative for this iteration.
- Access matrix already defines conflict.review.start, decision.create, decision.insufficient_data, decision.view and decision.supersede. No new roles or permissions. ADMIN alone never gains business authority.
- Existing auth has action permissions but no persisted domain grants. Add minimal explicit User.data_domains and an audited administrative scope assignment using existing user.manage/role.assign. New users default to no domain grant; legacy users' existing instance-wide data access is preserved explicitly as ["*"] by migration, not inferred from role names. Bootstrap ADMIN has explicit instance-wide read scope but still no decision authority. New Conflict/Decision read and review paths enforce stored domains; this is not a claim of a new multitenant isolation model for every historical ingestion API.

## Implementation boundaries

Modular monolith: new app/decisions module, same PostgreSQL and browser-cookie/HTTPS/Origin boundary. Row locking plus version token, unique immutable lineage and persistent actor/Conflict/idempotency-key identity protect concurrent reviewers/retries. Decision and lifecycle/audit commit together; failures cannot commit resolved-without-Decision. Selected values are resolved from the Conflict snapshot by immutable value ID, never accepted as arbitrary client truth. Corrected values use frozen kind/unit validation, preserve input/normalization trace, and do not mutate EntityValue/raw. Metadata snapshots/references retain both normalization origins, matching/config hashes and explicit unconfigured Forest Codex/authority.

No model weights, embedding, recommendation, RuleSuggestion, rule/Codex mutation, Publisher, production source credentials, write-back or native client. Existing user/default-stack data and historical reports remain intact. Tests use owned isolated schemas/projects. NFR metadata p95≤1s/10sessions and Conflict card≤2s apply; publish measured Decision-create latency without inventing an SLA.

Final acceptance still requires migration/recovery/concurrency/idempotency/negative scope/RBAC tests, actual browser/restart path, real screenshots, capacity measurements, security/production gates, independent retest and exact-final-head CI. Merge requires a separate owner instruction; Stage7 and issues18/20 are not implicitly accepted or closed.
