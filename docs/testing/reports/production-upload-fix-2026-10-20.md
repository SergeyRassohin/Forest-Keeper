# Исправление production upload и статуса этапа 2

База: main `52de12035f49cb887fccf2a3b7189f25411fa190`, 2026-10-20.

## Замечания и изменения

Production `/tmp` имел tmpfs 64 MiB при лимите файла 100000000 байт.
Multipart сначала принимает весь файл во временное хранилище; воспроизведение
на тех же версиях Starlette/python-multipart принимало 60 MiB, но 70 MiB
заканчивались ENOSPC. Простой запрос health и запись маленького marker этого не выявляли.

Backend теперь использует отдельный дисковый named volume `upload_tmp`, UID/GID 10001,
mode 0700, через `TMPDIR`. Worker/migrate не получают этот том. Существующий `import_files`,
read-only rootfs, tmpfs для остальных временных файлов и dev flow сохранены.
При ENOSPC/EDQUOT в multipart или записи оригинала возвращается безопасный HTTP 507
`STORAGE_FULL`. Временные файлы закрываются, незарегистрированный оригинал удаляется,
пакет не создаётся. После возврата свободного места загрузка проходит.

Dashboard описывает работающий импорт; документ прогресса фиксирует merge этапа 2
и отдельно сохраняет исторические результаты до hardening. Следующий этап — нормализация.

Всего 432 tests. Четыре новые интеграционные регрессии проверяют ENOSPC и EDQUOT
в multipart и fsync оригинала: безопасный ответ, закрытые tempfiles, отсутствие
незарегистрированных файлов/ImportBatch и успешная повторная загрузка после сбоя.

Production smoke на пересобранных образах использует собственный случайный project,
синтетическую БД/учётную запись/TLS и проверяет настоящий вход, создание источника и две
одновременные HTTPS multipart загрузки ровно по 100000000 байт. Barrier удерживает оба
запроса после передачи более 70 MB; файлы не выделяются целиком в RAM. Оба ответа201/QUEUED,
SHA-256 совпадают с переданными байтами, TMPDIR действительно указывает на дисковый том.
Worker во время загрузки остановлен; только тестовые queue deliveries удаляются до его
запуска, чтобы не импортировать миллионы синтетических строк. Это проверка приёма файлов,
а не benchmark фонового разбора 100 MB.

Также повторены существующие проверки production: реальные RQ задания, worker
healthy → frozen/unhealthy → stopped → restored, non-root/read-only/resources,
PG/Redis/original persistence. Проверка логов охватывает DB credentials и новые
синтетические пароль/сессионную cookie. Собственные контейнеры/volumes удаляются в finally;
общие сервисы не перезапускаются. Локальные browser tests используют существующее dev
окружение; CI повторяет их на окончательно пересобранных образах.

Независимая read-only проверка выполнена отдельным reviewer по AGENTS.md: повторены
4 новые регрессии, проверены Compose/TMPDIR/изоляция секретов и окончательный diff;
открытых замечаний нет. Полный runtime smoke выполнен основным агентом. CI окончательного
commit публикуется в PR. Это исправление двух замечаний,
без начала этапа 3 и изменений Authentication/RBAC.

## Эксплуатационные пределы

Дисковый том не задаёт квоту. Учитывайте параллельность и до примерно 200 MB свободного
места на активную загрузку при лимите 100 MB, отдельно от исторических оригиналов и БД.
Мониторинг места и ограничение входящей нагрузки остаются настройками сервера.
Подробности: [production profile](../../deployment/production-profile.md).
