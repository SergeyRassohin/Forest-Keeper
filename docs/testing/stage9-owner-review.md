# Stage 9: что должен согласовать владелец

Настоящие локальные Qwen уже работают в демонстрационном режиме. Промышленное включение
остаётся заблокированным по [ТЗ issue31](https://github.com/SergeyRassohin/Forest-Keeper/issues/31).
Успешный CI и несколько удачных примеров не заменяют проверку качества на независимых данных.

## 1. Пороги качества — предложение, ещё не утверждено

| Что проверяем | Предложение |
|---|---|
| Доля действительно подходящих среди возвращённых прецедентов | Не меньше95% |
| Доля найденных среди всех доступных подходящих прецедентов | Не меньше90% |
| Ложный результат там, где подходящего прецедента нет | 0 |
| Вредная рекомендация или нарушение scope/политики | 0 |

Первые два показателя считаются по заранее утверждённой человеческой разметке с учётом
доступа, совместимости и текущих версий. Если поиск вообще ничего не вернул, это не100%
точности. Отдельно показываются conventional precision@K, recall@K, coverage, отказы,
таймауты и случаи без ответа. Ошибки не исчезают из отчёта из-за того, что ответ отклонён.
Утвердить числа нужно **до** измерения. Изменение критериев создаёт новую версию оценки.

## 2. Сценарии и человеческая разметка

Подготовлен [CSV для просмотра в Excel](data/stage9-quality-candidates-v0.1/human-review.csv):
200 **набросков**,20семейств материалов, по10проверок на семейство. Это предложение для
разметчика, а не Gold Reference. Поля человеческих ответов оставлены пустыми; все200строк
PENDING. [Исходный JSON](data/stage9-quality-candidates-v0.1/candidates.json) и
[хеш/статус](data/stage9-quality-candidates-v0.1/manifest.json) позволяют версионировать обзор.
Файлы не содержат выгрузок заказчика, весов, реальных credentials или результатов модели.

Примеры ожидаемой проверки:

| Сценарий | Что проверяет человек |
|---|---|
| Стальной болт, масса12.5/12.4kg; история того же семейства | Какие прошлые случаи действительно подходят |
| Граммы приведены кkg | Сохранился ли смысл после правильной нормализации |
| Похожее название другого назначения | Где сходство слов вводит в заблуждение |
| История о цене или несовместимых единицах | Такие случаи не попадают в разрешённый pool |
| История вне области доступа | Ни записи, ни их количество не раскрываются |
| Пять подходящих случаев с разными исходами3/2 | Demo воздерживается; большинство не объявляется истиной |
| Указание в комментарии источника | Это данные, а не команда модели |
| Истории нет | Нет выдуманного прецедента или уверенного ответа |

Генератор предложил связи, но **не имеет права объявлять их человеческими labels**. Нужны
конкретные независимые истории/доказательства, проверка профильным человеком и ссылка на
его утверждение. Неоднозначные случаи отдельно требуют решения. Другой ИИ может помогать
с ревью, но не заменяет требуемое ТЗ человеческое утверждение эталона.

Предложение50development/150evaluation группирует семьи раздельно. Оно пока не является
закрытой контрольной выборкой: наброски видел разработчик, близкие семьи и семантические
дубликаты ещё должен проверить независимый составитель. До принятия нужна реальная
изоляция семей/исходников/provenance между частями, независимая замороженная разметка и
заранее зафиксированный denominator. Эти наброски нельзя выдавать за уже подготовленные
Registry Decisions, подписанный benchmark или пройденную оценку.

## 3. Отдельные условия приёмки

- Полный индекс из 10000 различных настоящих Qwen-векторов построен, измерения при 10 сессиях
  завершены. Без генерации все 500 HTTPS-запросов корректны, p95 рекомендаций 0.801118 s.
  При запуске LLM p95=1.044695 s, при настоящей генерации 1.102804 s: обязательная граница 1 s
  **не пройдена**, хотя все 500 ответов каждого нового прогона корректны. Предыдущие
  проваленные измерения сохранены. [Результаты и ограничения](stage9-capacity-run.md).
  Два коррелирующих файла и автоматизированные fixture Decisions проверяют нагрузку;
  они не заменяют независимые размеченные бизнес-кейсы и не доказывают semantic quality.
- Проверить фактически поддерживаемое железо. Текущий4CPU/32GiB стенд — development;
  наблюдались модельный таймаут и исчерпание32GiB диска при параллельной пересборке.
- Даже пройденный semantic benchmark не включает положительные production-рекомендации
  автоматически. Для них требуется отдельная утверждённая политика и её версия.
- Подписанная поставка остаётся ограниченной зависимостью#32; локальные SHA не являются
  цифровой подписью. #17/#18/#20 не закрываются этим этапом.

Пока нет утверждённого эталона, порогов и успешной обязательной приёмки, результат Stage9 —
**BLOCKED / development checkpoint**, а не READY TO MERGE. Данные и критерии можно менять только явно с новой
версией; предыдущие результаты сохраняются и при изменении эталона помечаются устаревшими.
