# Независимая проверка Authentication + RBAC — v0.1

Сценарий приёмки этапа 1 для [PR #3](https://github.com/SergeyRassohin/Forest-Keeper/pull/3). Проверять фактический HEAD PR; исторический отчёт для `ac1e7dc` находится в reports и относится к старому контракту. Текущий сценарий обновлён 19.10.2026 под единственный браузерный cookie-flow. После исправлений повторять затронутые сценарии и обязательные CI gates на новом коммите.

Документ описывает план проверки, а не выполненное ревью. Все результаты до запуска имеют статус **NOT RUN**. Проверяющий — человек или отдельная сессия ИИ, не участвовавшие в написании проверяемого изменения. Основание: [AGENTS.md](../../AGENTS.md), «Security-critical changes require independent verification».

## 2. Подготовка и фиксация среды

Использовать отдельную тестовую среду без реальных данных. Записать SHA HEAD/base, версии инструментов, дату UTC, конфигурацию лимитов и разрешённый Origin **без секретов**. Сверить запущенный образ с проверяемым исходным кодом. Не проводить разрушительные проверки на production или общей пользовательской БД.

1. Выполнить установку по локальной документации: frozen Python dependencies, `npm ci`, `bash scripts/dev-init.sh`, сборку и запуск Compose. В облаке с HTTPS proxy использовать `bash scripts/build-with-proxy.sh`. TLS-проверку не отключать.
2. Убедиться, что миграции дошли до `0002_auth`, `/api/v1/health` возвращает 200 и компоненты `ok`.
3. На отдельной пустой БД проверить bootstrap командой из authentication.md; пароль вводить скрыто. Для ручных проверок создать уникальные тестовые аккаунты: VIEWER, REVIEWER, DATA_OWNER, ADMIN, ADMIN+REVIEWER, без ролей. Использовать случайный префикс запуска и отдельные пароли.
4. Доступ к БД нужен только для проверки хранения, аудита и моделирования состояний, для которых ещё нет API. Такие изменения выполнять только над аккаунтами этого запуска, в отдельной тестовой БД. Не добавлять тестовые маршруты в production-приложение.

Команды из корня репозитория, с настроенным окружением согласно локальной документации:

```bash
bash scripts/check.sh
bash scripts/check-sast.sh
bash scripts/check-secrets.sh
bash scripts/test-security-gates.sh
bash scripts/check-dependencies.sh
bash scripts/check-integration.sh
```

Для установленного системного Chromium последнюю команду можно выполнить так:

```bash
FK_BROWSER_EXECUTABLE_PATH=/usr/bin/chromium bash scripts/check-integration.sh
```

Записать фактические числа passed/failed/skipped, exit codes и ссылки на CI **для того же SHA**. Нулевое число тестов и skipped не считать успешной проверкой. Автотесты используют временные схемы и собственные Redis keys; browser helper создаёт временные аккаунты и удаляет только свои fixtures. После аварийного завершения использовать документированный cleanup. Ручные аккаунты этим helper не очищаются.

## 3. Вход и ответы API

Каждый запрос выполнять в новом клиенте или явно очищать прежние cookie и Authorization, кроме сценариев, где требуется действующая сессия. API prefix: `/api/v1`. Для cookie-запросов на изменение задавать точный разрешённый Origin тестовой среды.

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| AUTH-01 | POST `/auth/login` с верными данными; GET `/auth/me`; повторить вход с логином в другом регистре | 200; тот же пользователь, актуальные роли/права; JSON содержит только user, cookie устанавливается; идентификатор сессии не присутствует в JSON |
| AUTH-02 | В отдельном клиенте неправильный пароль; затем неизвестный логин | Оба 401 с одинаковым публичным ответом `INVALID_CREDENTIALS`; новая сессия/cookie не создаётся; существование аккаунта не раскрывается |
| AUTH-03 | Для своего тестового пользователя выставить BLOCKED, затем DISABLED; пробовать верный пароль | В обоих случаях 401 с тем же общим сообщением; вход запрещён |
| AUTH-04 | Отправить malformed JSON, лишние поля, пустые обязательные поля, пароль более 128 символов | 422; ответ не отражает пароль, token или traceback; данные и сессии не создаются |
| AUTH-05 | Без сессии запросить `/auth/me`, `/dashboard`, `/users`, `/version`; POST `/users` с корректным телом | 401; нет пользовательских/административных данных. Публичный `/health` остаётся 200 при исправной среде и не содержит credentials |
| AUTH-06 | Прочитать auth/user ответы, включая ошибки | `Cache-Control: no-store`; UserView не содержит password_hash; 401 не рекламирует Bearer; login schema не содержит access_token/token_type |

## 4. Сессии, браузер и CSRF

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| SESSION-01 | После входа проверить Set-Cookie и DevTools Storage | `__Host-fk_session`: Secure, HttpOnly, SameSite=Strict, Path=/, без Domain. Нет token/пароля в localStorage/sessionStorage; JS не читает HttpOnly cookie |
| SESSION-02 | Перезагрузить страницу; затем выйти через UI, обновить страницу и повторно предъявить сохранённую cookie | После перезагрузки вход сохраняется; logout 204, cookie удалена; старая cookie даёт 401 |
| SESSION-03 | Проверить случайный, изменённый, слишком длинный token и неверную схему Authorization | 401. Даже корректный идентификатор действующей сессии в Authorization без cookie не аутентифицирует клиента; с cookie заголовок Authorization также отклоняется |
| SESSION-04 | В тестовой БД установить `expires_at` своей сессии в прошлом; повторить API/UI запрос | 401; интерфейс предлагает вход. Ошибка связи с API показана отдельно от отсутствия авторизации |
| SESSION-05 | После входа выставить BLOCKED/DISABLED своему аккаунту и повторить запрос с прежним token | Немедленный 401, без ожидания истечения сессии |
| CSRF-01 | С действующей cookie POST `/auth/logout` и `/users` без Origin, затем с `https://evil.invalid` | 403 `ORIGIN_NOT_ALLOWED`; сессия не отозвана, пользователь не создан |
| CSRF-02 | POST login без Origin, с Origin null и запрещённым Origin; повторить с разрешённым | Отсутствующий/null/запрещённый Origin даёт 403 без новой сессии; разрешённый допускает обычную проверку credentials |
| CSRF-03 | Без cookie передать действующий идентификатор сессии в Authorization; с cookie попытаться POST без Origin/с Origin null | Заголовок не авторизует клиента: 401; cookie-запрос без разрешённого Origin: 403; изменения в БД отсутствуют |
| WEB-01 | Проверить gateway headers и попытку встроить UI в чужой iframe | CSP ограничивает ресурсы своим origin; frame запрещён CSP frame-ancestors и X-Frame-Options. Проверить отсутствие permissive стороннего CORS |
| WEB-02 | Ввести неверный пароль; проверить UI после ответа; смоделировать сетевую ошибку | Пароль очищается после попытки, сообщение понятно; сетевая ошибка не маскируется успешным входом |

Login передаёт идентификатор сессии только через HttpOnly Set-Cookie. В JSON и OpenAPI-схеме ответа нет access_token/token_type. Не прикладывать cookie или пароль к отчёту/HAR.

## 5. RBAC и управление пользователями

Ожидаемые ответы реальных маршрутов для действующих сессий:

| --- | --- | --- | --- | --- | --- |
| GET `/auth/me` | 200 | 200 | 200 | 200 | 200 |
| GET `/dashboard` | 200 | 200 | 200 | 200 | 403 |
| GET `/users` | 403 | 403 | 403 | 200 | 403 |
| GET `/version` | 403 | 403 | 403 | 200 | 403 |

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| RBAC-01 | Выполнить таблицу прямыми API-запросами, независимо от видимости кнопок | Все результаты совпадают; запрещённые POST не меняют БД |
| RBAC-02 | Независимо прочитать XLSX, сравнить все 39 permissions с runtime-каталогом и выполнить параметризованные проверки 4 ролей + без ролей | 195 комбинаций соответствуют XLSX; неизвестный permission запрещён; SHA каталога соответствует XLSX |
| RBAC-03 | Проверить ADMIN, затем ADMIN+REVIEWER | ADMIN один не получает `decision.create`, `match.review`, `recommendation.accept_as_decision`; сочетание ролей даёт объединение прав по матрице. `rule.activate` не выводится из имени ADMIN |
| RBAC-04 | Удалить роль своего аккаунта в тестовой БД; повторить `/auth/me` и защищённый запрос прежней сессией | Права обновляются сразу; пользователь без ролей получает 403 на `/dashboard` |
| USER-01 | ADMIN создаёт пользователя с REVIEWER; войти этим пользователем | 201; правильная роль; пароль хранится хешем; новый пользователь получает свои права без административных |
| USER-02 | Создать пользователя с повторёнными ролями; затем повторить тот же login, включая вариант регистра | Роли дедуплицированы; дубликат login даёт 409; второй пользователь не создаётся |
| USER-03 | Передать `SUPER_ADMIN`, status/password_hash или иное лишнее поле; пароль короче 12 либо длиннее 128 символов | 422; нет частично созданного аккаунта/ролей; секреты не отражены |
| USER-04 | Сессию ADMIN сделать старше 5 минут, сохранив expires_at в будущем; POST `/users`; после повторного входа повторить | Первый запрос 403 `REAUTH_REQUIRED`, без записи в БД; после нового входа 201 |
| USER-05 | Проверить панель ADMIN и UI обычных ролей; создать аккаунт через UI | Панель соответствует правам, создание работает; ограничение сервером сохраняется при ручном обходе UI |

Для будущих бизнес-permissions пока нет продуктовых endpoints. Их проверки в test-only маршрутах подтверждают policy/dependency, **не** приёмку будущих решений, импорта или object scope. Существующие продуктовые маршруты дополнительно проверять напрямую. Изменение ролей и статуса через UI/API в этот этап не входит.

| --- | --- | --- |
| BOOT-01 | На отдельной пустой БД выполнить bootstrap с валидным паролем; проверить User/UserRole и AuditEvent | Один ADMIN без бизнес-ролей; Argon2id; `ADMIN_BOOTSTRAPPED`: actor `user_id=NULL`, target `object_id` равен новому User |

| STORE-01 | Сопоставить секреты своих тестовых аккаунтов с соответствующими строками БД, не выводя значения | Password hash Argon2id с документированными параметрами; AuthSession хранит SHA-256 идентификатора сессии, не исходное значение; разные входы имеют разные значения cookie |

| AUDIT-02 | Сравнить payload событий и логи со своими credentials внутри проверяющего процесса | Нет паролей, raw tokens и cookie; назначенные роли зафиксированы без секретов |
| AUDIT-03 | В отдельных транзакциях попытаться UPDATE и DELETE тестового AuditEvent под runtime DB-role; после ошибки rollback | Оба отклоняются append-only trigger; событие сохранено неизменным. Не считать trigger защитой от владельца БД, способного отключить его |

## 7. Лимиты и отказы

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| FAIL-01 | В отдельной конфигурации задать account limit=2, window=73; сделать три попытки входа на один аккаунт; повторить после окна | Первые две обрабатываются нормально, третья 429 `LOGIN_RATE_LIMITED`, Retry-After=73; после окна вход снова проверяется |
| FAIL-02 | На отдельной среде проверить IP limit несколькими разными логинами; пробовать подменять X-Forwarded-For | Общий peer IP лимит действует; произвольный X-Forwarded-For не позволяет обход. Записать известное ограничение: за proxy клиенты могут делить peer IP лимит |
| FAIL-03 | В отдельной среде отключить Redis; попытаться войти; затем восстановить сервис | Login 503 `AUTH_UNAVAILABLE`, без новой сессии и обхода лимитов; после восстановления обычное поведение возвращается |
| FAIL-04 | Остановить PostgreSQL отдельной среды; запросить health и защищённый API; восстановить БД | Health 503; авторизация не разрешает доступ при отказе БД, credentials/traceback не раскрываются; после восстановления запросы возвращаются к норме |

Не останавливать общие сервисы. Перед следующим сценарием восстановить состояния собственных аккаунтов/сессий, настройки и сервисы. Не очищать Redis целиком.

## 8. Итог и критерии приёмки

Для каждого ID фиксировать **PASS / FAIL / BLOCKED / NOT RUN**, evidence и SHA. Проверки хранения, гонки bootstrap, IP limit и отказов сервисов не считать выполненными только потому, что похожий автотест зелёный. При FAIL дать минимальное воспроизведение, ожидаемое/фактическое поведение, влияние и ссылку на код.

Этап можно принять после независимого отчёта, успешных обязательных gates на актуальном SHA и устранения воспроизводимых дефектов, нарушающих сценарий и требования безопасности. BLOCKED/NOT RUN в обязательных проверках требуют завершения проверки; они не равны PASS. Исключения оформляются явным решением по правилам Testing Strategy, а не устным утверждением автора кода.

Отдельно зафиксировать границы этапа: нет MFA/SSO/password recovery, редактирования аккаунтов через UI, business object scope и продуктовых бизнес-endpoints. Recent authentication не заменяет MFA. Эта проверка не заменяет независимый pentest перед промышленным пилотом.

Шаблон отчёта:

```text
PR / HEAD SHA / base SHA:
Проверяющий и независимость от автора:
Дата UTC / среда / версии / конфигурация без секретов:
CI URL для HEAD / команды и результаты:

ID | Статус | Фактический результат | Evidence без секретов
...

Замечание: ID, severity и обоснование
Предусловия и шаги воспроизведения:
Ожидаемый / фактический результат:
Влияние / файл:строка / доказательство без credentials:

BLOCKED / NOT RUN и причина:
Проверки после исправлений и новый SHA:
Вывод: принять / вернуть на исправление / проверка не завершена.
```

После проверки очистить только собственные тестовые аккаунты и их сессии, безопасно удалить локальные файлы credentials; аудит сохранить. Не удалять volumes с пользовательскими данными и не переписывать историю AuditEvent.
