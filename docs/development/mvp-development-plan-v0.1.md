# Forest Keeper — MVP Development Plan v0.1

Статус: обязательный план реализации MVP.

## 1. Цель MVP

MVP должен доказать один полный рабочий сценарий:

```text
два источника данных
→ импорт и сохранение raw
→ нормализация
→ сопоставление сущностей
→ обнаружение конфликта
→ поиск похожих подтверждённых решений
→ рекомендация FK
→ Human Review
→ решение человека
→ сохранение решения в Decision Registry
→ использование этого решения в следующем похожем случае
```

MVP не должен писать обратно в 1С, Excel, CRM или другие production-системы.

---

## 2. Что считается успехом MVP

MVP считается успешным, если можно воспроизводимо показать следующий сценарий:

1. Пользователь загружает два набора данных об одних и тех же сущностях.
2. FK сохраняет исходные файлы и provenance.
3. FK разбирает и нормализует данные.
4. FK сопоставляет записи из разных источников.
5. FK обнаруживает конфликт по атрибуту.
6. FK показывает источник, исходные и нормализованные значения.
7. FK находит похожие прошлые решения, если они есть.
8. FK формирует объяснимую рекомендацию.
9. Пользователь принимает решение.
10. Решение сохраняется с контекстом и пользователем.
11. При следующем похожем конфликте FK использует это подтверждённое решение как прецедент.
12. Весь путь виден в Audit.

Если пункт 11 не работает, основная продуктовая гипотеза Forest Keeper не доказана.

---

## 3. Ограничения первой версии

В MVP входят:
- Web Client;
- локальная аутентификация;
- роли VIEWER / REVIEWER / DATA_OWNER / ADMIN;
- PostgreSQL;
- pgvector;
- Redis + RQ;
- импорт XLSX / CSV / XML;
- целевой сценарий 1С XML + Excel/CSV;
- локальное файловое хранилище;
- Decision Registry;
- Similarity;
- Recommendation Engine;
- подключаемый локальный AI/LLM provider;
- лицензирование;
- базовый Update Service;
- Audit;
- автоматические тесты.

Не входят:
- production write-back;
- сложные CRM/ERP API-коннекторы;
- Kafka;
- Kubernetes;
- отдельная vector DB;
- GraphQL;
- микросервисное дробление;
- мобильный клиент;
- сложная HA/DR инфраструктура;
- автоматическое изменение правил без человека.

# Этап 0. Подготовка репозитория

## Цель
Получить запускаемый каркас проекта, одинаковый для Codex и разработчика.

## Реализовать
- создать структуру `backend/`, `frontend/`, `deploy/`, `tests/e2e/`;
- настроить Python 3.13;
- FastAPI;
- React + TypeScript + Vite;
- PostgreSQL;
- Redis;
- Docker Compose;
- базовую конфигурацию через environment;
- Alembic;
- pytest;
- Vitest;
- Playwright;
- линтеры и форматирование;
- health endpoint.

## Проверка
- `docker compose up` поднимает весь минимальный контур;
- frontend открывается;
- backend отвечает на `/api/v1/health`;
- backend подключается к PostgreSQL и Redis;
- тестовая миграция применяется.

## Definition of Done
Новый разработчик или Codex может получить репозиторий и одной документированной последовательностью запустить систему локально.

# Этап 1. Аутентификация и роли

## Реализовать
- User;
- UserRole;
- локальный login;
- secure password hashing;
- session/access token;
- RBAC middleware/dependency;
- роли VIEWER / REVIEWER / DATA_OWNER / ADMIN;
- `POST /api/v1/auth/login`;
- `GET /api/v1/auth/me`.

## Проверка
- пользователь входит;
- неверный пароль отклоняется;
- защищённый API недоступен без авторизации;
- роль ограничивает действие.

## Definition of Done
Frontend знает текущего пользователя и его роли, backend проверяет права на каждой защищённой операции.

---

# Этап 2. Источники и импорт

## Реализовать
- SourceSystem;
- ImportBatch;
- RawRecord;
- файловое хранилище;
- checksum;
- provenance;
- импорт XLSX;
- импорт CSV;
- импорт XML;
- базовый адаптер выгрузки 1С XML;
- background processing через RQ.

API:
- `POST /api/v1/imports`;
- `GET /api/v1/imports/{id}`;
- `GET /api/v1/imports/{id}/errors`.

## Проверка
- файл загружается;
- оригинал сохраняется;
- повторная загрузка определяется по checksum;
- строки/объекты превращаются в RawRecord;
- ошибки импорта не уничтожают весь пакет;
- provenance сохраняется.

## Definition of Done
Два разных файла можно загрузить, после чего FK показывает оба пакета и исходные записи без потери исходных значений.

---

# Этап 3. Нормализация и каноническая модель

## Реализовать
- CanonicalEntity;
- EntityValue;
- маппинг source fields → canonical attributes;
- нормализацию строк;
- регистр;
- whitespace;
- даты;
- decimal;
- единицы измерения;
- исходное и нормализованное значение хранятся одновременно.

## Проверка
Примеры:
- `12,5 кг`;
- `12500 г`;
- `12.500 KG`;

приводятся к сопоставимому внутреннему представлению, но raw остаётся неизменным.

## Definition of Done
FK может показать пользователю одновременно:
- исходное значение;
- нормализованное значение;
- источник;
- правило/операцию нормализации.

---

# Этап 4. Matching / Entity Resolution

## Реализовать
- MatchCandidate;
- exact matching;
- rule-based matching;
- fuzzy matching;
- similarity score;
- статус кандидата;
- порог auto-match;
- порог needs-review.

Embeddings на этом этапе допускаются как дополнительный механизм, но не должны быть единственным способом сопоставления.

## Проверка
Набор тестовых записей должен включать:
- точные совпадения;
- различия написания;
- близкие, но разные сущности;
- заведомые false merge cases.

## Definition of Done
FK умеет разделить:
- MATCHED;
- POSSIBLE_MATCH / NEEDS_REVIEW;
- NOT_MATCHED;

и хранит основания сопоставления.

---

# Этап 5. Conflict Engine

## Реализовать
- Conflict;
- типы:
  - VALUE_MISMATCH;
  - DUPLICATE;
  - FORMAT;
  - MISSING;
- severity;
- status;
- Basis;
- связь с canonical entity;
- связь с source values.

API:
- `GET /api/v1/conflicts`;
- `GET /api/v1/conflicts/{id}`.

## Проверка
Для одной канонической сущности:
- значение в источнике A отличается от источника B;
- FK создаёт один объяснимый Conflict;
- в карточке видны оба значения и provenance.

## Definition of Done
Пользователь может открыть конфликт и понять:
- что именно не совпало;
- где;
- какие значения сравнивались;
- почему FK считает это проблемой.

---

# Этап 6. Human Review UI

## Реализовать
Web-экран конфликта:
- сущность;
- атрибут;
- raw values;
- normalized values;
- источники;
- Basis;
- similarity evidence;
- Recommendation;
- комментарий;
- действия:
  - принять рекомендацию;
  - выбрать значение источника;
  - указать другое значение;
  - недостаточно информации.

## Проверка
REVIEWER / DATA_OWNER может принять решение.
VIEWER не может.

## Definition of Done
Конфликт можно полностью разобрать через браузер без прямой работы с БД или API вручную.

---

# Этап 7. Decision Registry

## Реализовать
- Decision;
- user_id;
- conflict_id;
- decision_type;
- selected_value;
- comment;
- decision_context;
- created_at;
- неизменяемая история решений;
- Audit event.

API:
- `POST /api/v1/conflicts/{id}/decisions`;
- `GET /api/v1/conflicts/{id}/decisions`.

## Проверка
После решения сохраняются:
- значения источников;
- состояние правил;
- тип сущности;
- атрибут;
- выбранный результат;
- пользователь;
- время;
- комментарий.

## Definition of Done
Даже если позже данные, шаблон или правила изменились, можно восстановить, на каком контексте было принято конкретное решение.

---

# Этап 8. Similarity по прошлым решениям

## Реализовать
- embedding representation decision context;
- pgvector;
- SimilarityService;
- поиск похожих Decision;
- similarity score;
- threshold;
- top-N retrieval.

API:
- `GET /api/v1/conflicts/{id}/similar-decisions`.

## Проверка
Для заранее подготовленных похожих и непохожих конфликтов:
- похожие решения поднимаются выше;
- явно нерелевантные не попадают в top-N при установленном threshold.

## Definition of Done
Новый конфликт получает список реально похожих подтверждённых решений с оценкой сходства.

---

# Этап 9. Recommendation Engine

## Реализовать
Recommendation Engine получает:
- текущий Conflict;
- действующие Rules;
- CustomerTemplate;
- похожие Decisions;
- similarity score;
- Authoritative Source, если задан.

Он формирует:
- recommended_action;
- confidence;
- reasoning_summary;
- references to similar decisions;
- rules used.

API:
- `GET /api/v1/conflicts/{id}/recommendation`.

## Правило
Recommendation никогда сама не меняет данные и не создаёт Decision.

## Проверка
При наличии 5 похожих решений, где пользователь выбирал один и тот же источник, Recommendation должна:
- предложить соответствующее действие;
- сослаться на историю;
- объяснить основание.

## Definition of Done
Пользователь видит не просто "AI считает", а конкретное объяснение:
"В 5 похожих подтверждённых случаях вы выбирали значение из 1С".

---

# Этап 10. AI / LLM provider

## Реализовать
- `LLMProvider`;
- `EmbeddingProvider`;
- Local provider;
- OpenAI-compatible transport как технический интерфейс;
- structured JSON output;
- timeout;
- fallback;
- audit технических ошибок.

## AI используется для
- объяснения рекомендации;
- текстового анализа контекста;
- обобщения похожих решений;
- подготовки предложения формального правила.

## AI не используется для
- хранения enterprise memory;
- скрытого изменения Rules;
- записи в production;
- принятия финального решения.

## Проверка
При недоступности LLM:
- конфликт по-прежнему открывается;
- Decision Registry работает;
- rule-based / similarity recommendation не ломает весь сценарий.

## Definition of Done
AI является заменяемым помощником, а не точкой отказа всей системы.

---

# Этап 11. Rules и Customer Template

## Реализовать
- Rule;
- CustomerTemplate;
- базовый шаблон FK;
- активный шаблон клиента;
- ручное изменение правил;
- origin:
  - FK_DEFAULT;
  - CUSTOMER;
  - LEARNED_PROPOSAL.

## Проверка
- клиент может работать на базовом шаблоне;
- изменение шаблона влияет на последующий анализ;
- изменение логируется.

## Definition of Done
Правила клиента управляются отдельно от исходного кода и версионируются.

---

# Этап 12. Предложение формализовать повторяющуюся практику

## Реализовать
Если в похожих случаях пользователь устойчиво принимает однотипное решение, FK может создать RuleSuggestion.

Пример:
```text
12 из 12 похожих решений:
Material.mass → использовать 1С
```

Действия:
- Accept;
- Reject.

После Accept создаётся или изменяется Rule.

## Правило
Автоматическая активация правила без подтверждения запрещена.

## Definition of Done
FK не только вспоминает прошлое решение, но способен предложить превратить устойчивую практику в явное правило клиента.

---

# Этап 13. Audit

## Реализовать
AuditEvent для:
- login;
- import;
- normalization;
- match;
- conflict;
- recommendation;
- decision;
- rule change;
- template change;
- license action;
- admin action.

## Проверка
Для выбранного Decision можно восстановить цепочку:
```text
Source → Import → Raw → Normalization → Match → Conflict → Recommendation → Decision
```

## Definition of Done
Аудит позволяет объяснить происхождение результата без просмотра внутренних логов приложения.

# Этап 14. Лицензирование

## Реализовать
Client side:
- License Service;
- загрузка `forestkeeper.license`;
- verify signature;
- validity;
- edition;
- modules;
- limits;
- ACTIVE / GRACE_PERIOD / READ_ONLY.

Supplier side:
- каркас отдельного `license-generator/`;
- private key никогда не попадает в клиентский runtime.

## Проверка
- корректная лицензия принимается;
- подделанная отклоняется;
- expired license переходит в ожидаемый режим;
- данные клиента остаются доступны согласно принятой модели.

## Definition of Done
MVP можно поставить заказчику с рабочей offline-лицензией.

Минимум:
- version check;

- backup;
- DB migration;
- service restart;
- health check;
- rollback.

Поддержать:
- offline package;
- online source как опциональный режим.

## Definition of Done
Тестовое обновление может быть применено и откатано без ручной правки БД.

# Этап 16. Финальный E2E

## Обязательный сценарий

### Итерация 1
1. Загрузить 1С XML.
2. Загрузить Excel/CSV.
3. FK создаёт RawRecord.
4. Нормализует.
5. Сопоставляет.
6. Находит Conflict.
7. Recommendation сообщает, что истории пока нет.
8. Пользователь принимает решение.
9. Решение сохраняется.

### Итерация 2
10. Загрузить новый похожий набор.
11. FK создаёт похожий Conflict.
12. Similarity находит Decision из итерации 1.
13. Recommendation ссылается на предыдущее решение.
14. Пользователь видит:
   "В прошлый раз в похожей ситуации было принято решение X".
15. Пользователь подтверждает или выбирает другой вариант.

## Definition of Done
Сценарий полностью проходит через UI и автоматически проверяется Playwright-тестом.

# 5. Правило для Codex

Codex должен работать короткими законченными итерациями.

Для каждого этапа:
1. прочитать связанные документы;
2. реализовать минимально достаточный объём;
3. написать/обновить тесты;
4. запустить тесты;
5. проверить diff;
6. обновить документацию, если реализация потребовала уточнения;
7. commit;
8. только потом переходить дальше.

Если реализация требует решения, которого нет в документации, Codex не должен молча придумывать его.

Он должен:
- зафиксировать вопрос;
- остановить спорную часть;
- продолжить независимую работу, если возможно.

# 6. Definition of Done всего MVP

MVP готов, когда одновременно выполнены условия:

- проект разворачивается по документированной процедуре;
- Web Client работает;
- RBAC работает;
- импортируются два источника;
- raw и provenance сохраняются;
- нормализация воспроизводима;
- matching объясним;
- conflicts создаются;
- Human Review работает;
- Decision Registry хранит решения;
- Similarity находит прошлые решения;
- Recommendation использует историю;
- AI заменяем и не является memory;
- Rules не меняются без подтверждения;
- Audit восстанавливает цепочку;
- license verification работает;
- update smoke-test работает;
- обязательный E2E проходит автоматически;
- исходные production-системы остаются read-only.

Главный критерий:
**второй похожий конфликт должен быть обработан умнее первого за счёт подтверждённого решения пользователя, а не за счёт магического "AI так решил".**
