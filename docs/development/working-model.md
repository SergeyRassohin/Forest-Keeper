# Рабочая модель Forest Keeper

## 1. Где обсуждать
Обсуждать продукт, требования, архитектуру, интерфейс и спорные решения удобно в ChatGPT.

## 2. Где фиксировать
GitHub — единственный официальный источник истины проекта.

Любая существенная договорённость после обсуждения должна попасть в один из документов репозитория:
- требования;
- архитектура;
- decision log;
- workflow;
- интерфейс;
- тестирование;
- безопасность.

Сырые разговоры не являются спецификацией.

## 3. Где генерировать документацию
Документацию можно обсуждать и генерировать в ChatGPT, но окончательная версия должна сохраняться в GitHub в Markdown.

Word/PDF/PowerPoint используются как представление для заказчиков, инвесторов и внешних людей, но не как основной инженерный источник.

## 4. Где вести разработку
Разработка ведётся в Codex в локальном клоне репозитория.

Типовой цикл:

1. Обсуждаем идею в ChatGPT.
2. Фиксируем решение в GitHub.
3. Codex делает `git pull`.
4. Codex реализует изменение в отдельной ветке.
5. Тесты и проверки.
6. Commit / PR.
7. Ревью результата.
8. Merge в `main`.
9. Документация и decision log обновляются при необходимости.

## 5. Что считать истиной при конфликте
Приоритет:

1. последние явные решения в `docs/decisions/decision-log.md`;
2. актуальные требования;
3. актуальная архитектура;
4. старые документы и презентации;
5. сырые обсуждения в чате.

Если документы противоречат друг другу, Codex не должен угадывать. Он должен поднять конфликт.
