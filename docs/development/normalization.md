# Stage 3 — normalization and canonical representation

Спецификация: [issue #12](https://github.com/SergeyRassohin/Forest-Keeper/issues/12). На этом этапе один `RawRecord` получает отдельное pre-match представление. Записи разных источников не объединяются, истина и authoritative source не определяются. Matching относится к этапу 4.

## Работа в браузере

В разделе «Импорт данных» откройте завершённый пакет CSV/XLSX/XML. В блоке «Нормализация» выберите профиль и нажмите «Нормализовать пакет». Запуск доступен REVIEWER, DATA_OWNER и ADMIN через существующее право `analysis.run`; VIEWER имеет только `analysis.view`.

После завершения раскройте запись. Для каждого атрибута показаны фактическое исходное значение, нормализованное значение, единица, качество, путь поля и правило преобразования. Ниже доступны неизменённый raw payload, источник, пакет, позиция и SHA-256 оригинала. Неизвестные поля и неподдержанные типы объектов видны в диагностике и сохраняются в raw.

`VALID`, `WARNING`, `INVALID`, `UNKNOWN` — единственные состояния качества. Неоднозначность не разрешается догадкой. Счётчики качества относятся к EntityValue; неизвестные поля учитываются отдельно в диагностике mapping. У незавершённого запуска результаты частичные.

## Профили

Декларативные JSON находятся в `backend/app/normalization/profiles/`. Исполняемые выражения не поддерживаются. Профиль задаёт UUID, версию, domain/entity_type, binding по формату/source_type/object_type и literal path каждого атрибута. Движок фиксирован версией `fk-normalization/1`.

`synthetic-material-v1` — синтетическая демонстрация для CSV, первого листа XLSX, generic XML и тестового профиля 1С XML. Поля: code, name, mass, price, manufactured_on. Это не согласованный pilot domain и не описание реальной выгрузки заказчика. `synthetic-capacity-v1` используется только для измерений 30 атрибутов. Для реального пилота нужен отдельный профиль после согласования domain и примера выгрузки.

Пробелы, Unicode NFC и регистр обрабатываются только по объявленным правилам. Missing, JSON null и пустая строка различаются в `normalization_rule.presence`. Decimal хранится стабильной строкой: точная арифметика Decimal, без округления и вычислений float. Смешанные разделители, неизвестные единицы, выход за пределы и неоднозначные даты дают диагностический статус. Единицы перечислены явно: `12,5 кг`, `12500 г`, `12.500 KG` → `12.5 kg`. XLSX float отмечается WARNING/DECODED_FLOAT, поскольку точность могла быть утрачена до нормализации. Даты остаются календарными датами без выдуманного часового пояса; midnight преобразуется только при явно разрешённой политике, с WARNING.

## Хранение и повторы

Миграция `0004_normalization` добавляет AnalysisRun, CanonicalEntity, EntityValue и техническую связь AnalysisRecord; raw/import таблицы сохраняются. Entity.status остаётся NULL: бизнес-жизненный цикл этого поля ещё не согласован. Нового бизнес-enum нет.

AnalysisRun использует существующий lifecycle NEW → QUEUED → PROCESSING → COMPLETED/FAILED. POST `/api/v1/analysis` принимает существующие `import_batch_ids` и `template_id` (UUID конфигурационного профиля). Конкурентные одинаковые активные запросы получают один запуск; после терминального состояния явный POST создаёт новую историю. Полный snapshot правил, версия движка и hash фиксируются навсегда.

CanonicalEntity и EntityValue неизменяемы. UUID зависит от RawRecord и hash профиля: повтор той же версии переиспользует факты, новая версия создаёт новые, старые доступны через старый запуск. Обработка идёт страницами по 100 записей; записи, значения, связь и прогресс фиксируются одной транзакцией. После жёсткого прерывания PROCESSING может продолжиться с последнего checkpoint без дублирования.

Worker проверяет потерянные запуски при старте и периодически через штатное RQ maintenance. Защитное окно — 60 секунд; maintenance interval — 30 секунд, idle dequeue может ждать до 105 секунд. На занятом единственном worker проверка выполняется после текущего задания; это не обещание восстановления за 60 секунд. NEW повторно публикуется; потерянные QUEUED/PROCESSING завершаются безопасным FAILED/NORMALIZATION_INTERRUPTED, после чего пользователь явно запускает повтор. CLI: `python -m app.normalization.recover`. Ошибки не раскрывают содержимое исходных данных. Аудит фиксирует автора, scope, версии и переходы без полного raw payload.

## Проверка

Общие команды — `scripts/check.sh`, `scripts/check-integration.sh` и обязательные security gates. Fixtures/ожидаемые результаты: `tests/data/normalization/`. Browser E2E проверяет CSV + 1С XML, три эквивалентные массы, диагностику, provenance, сохранность raw и VIEWER.

Нагрузочная проверка выполняется только на disposable development PostgreSQL/Redis, с `FK_TEST_INTEGRATION=1`: из backend `uv run python -m tests.benchmark_normalization --records 100 1000 10000 100000`. Для каждого размера создаются два набора по 30 атрибутов существующим генератором; реальные API/RQ/DB, 10 сессий и metadata p95 ≤ 1 секунды. Собственные schema, файлы и очереди удаляются после проверки. Это профиль нормализации, а не приёмка производительности всего MVP.

Upgrade с 0003 и повторный upgrade безопасны; downgrade проверяется только на собственном fixture. Downgrade удаляет историю нормализации, поэтому для сервера нужен backup/операционный план, а не автоматический откат с потерей результатов.
