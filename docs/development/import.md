# Этап 2: источники и импорт

Реализация по [issue #7](https://github.com/SergeyRassohin/Forest-Keeper/issues/7). Пользователь входит через браузер, открывает «Импорт данных», создаёт источник при наличии source.manage, выбирает файл и наблюдает фоновую обработку. Карточка показывает оригинальное имя, источник, SHA-256, пользователя/UTC-время загрузки, статус, ошибки и исходные записи с provenance. Нормализация и следующие бизнес-этапы сюда не входят.

## Модель и контракт

Миграция `0003_imports` добавляет SourceSystem, ImportBatch, RawRecord и технические ImportErrorRecord. Канонические статусы ImportBatch: NEW → QUEUED → PROCESSING → COMPLETED / COMPLETED_WITH_ERRORS / FAILED; QUEUED → FAILED допустим при отказе очереди. NEW не превращается напрямую в FAILED.

Канонический SourceSystem задаёт source_type как Enum без полного списка значений. Для текущего файлового MVP API уточняет минимальные типы FILE (обычные файлы) и ONE_C (тестовая XML-выгрузка 1С). Это уточнение зафиксировано в decision log и API. Source status создаётся ACTIVE; канонические DISABLED/ARCHIVED распознаются при проверке загрузки. API настройки меняет имя/authority_scope, но не вводит самовольные переходы статуса. Пустой authority_scope означает, что назначение авторитетного источника пока не задано; импорт не устанавливает истинность значений.

RawRecord содержит исходный payload, ключ/тип записи и source_position. Позиция → ImportBatch → SourceSystem → checksum/сохранённый файл восстанавливают происхождение. PostgreSQL trigger запрещает UPDATE/DELETE RawRecord, как и аудит; отдельный trigger защищает оригинальные metadata ImportBatch от изменения. Пользовательского удаления файлов/пакетов/исходных записей нет. Владельца БД/файлового тома эти ограничения не заменяют.

## Файлы и пределы

Backend и worker используют один persistent volume `import_files`, смонтированный в `/var/lib/forest-keeper/imports` с владельцем UID10001. На хосте default `backend/var/imports` игнорируется Git; для своего каталога задайте FK_IMPORT_STORAGE_ROOT.

Файлы получают сгенерированный UUID-ключ. Пользовательское имя хранится отдельно и не попадает в filesystem path; slash, backslash, colon, control characters, имена длиннее255 отклоняются. Создание эксклюзивное, без перезаписи; после fsync файл получает mode0400. SHA-256 читается по сохранённым байтам и снова сверяется worker перед разбором. Изменённый оригинал не обрабатывается как успешный импорт.

- FK_IMPORT_MAX_BYTES: 100000000 байт по умолчанию (инженерный профиль100MB). Streaming multipart-body ограничен этим размером плюс64KiB служебных данных; файл проверяется отдельно. Gateway принимает тело до101MiB и не требует завершения разбора в HTTP-запросе.
- FK_IMPORT_MAX_EXPANDED_BYTES: 512000000 для суммарного распакованного XLSX; не более10000 ZIP-элементов и ratio200 на элемент. Worksheet XML проверяется до openpyxl: позиции строк в пределах1048576, не более1000пустых позиций подряд, колонки1–1024, без повторных/неупорядоченных координат; глубина XML≤64. Это ограничивает работу на маленьких sparse-row/column bombs, а не только размер ZIP. Запрещены traversal, duplicate ZIP names, encrypted entries и VBA project. .xls/.xlsm и прочие форматы не принимаются.
- Одна исходная запись вместе с подробной metadata ограничена1MB. Непредставимые в PostgreSQL значения (например, NUL) и слишком длинный тип XML-объекта становятся ошибкой конкретной записи. Оригинал сохраняет её фактическое содержимое.
- Списки/API страницы: default50, максимум100, offset до1000000; UI листает пакеты, записи и ошибки по50. Селектор источников показывает первые100 источников; расширение выбора сверх этого MVP-ограничения потребует отдельного UI.

## Поддерживаемые профили

CSV: UTF-8/UTF-8 BOM, разделитель запятая, первая строка — непустые уникальные текстовые заголовки. Quoted separators/newlines обрабатываются csv.reader(strict=True). Все значения остаются строками, включая пробелы и ведущие нули. Пустые физические строки пропускаются; quoted empty cells являются значениями. source_position содержит фактические line_start/line_end, включая многострочную запись. Некорректное число колонок — ошибка строки. Нечитаемая кодировка/заголовок или обрыв структуры могут завершить пакет FAILED; ранее сохранённые chunks остаются.

XLSX: первый worksheet в порядке workbook, первая строка — уникальные текстовые заголовки; остальные листы не импортируются. Пустые строки пропускаются, отсутствующие ячейки становятся null. Сохраняются typed cell values и формулы как текст, без вычисления/запуска; source_position включает sheet/row, cell_types и number_formats. Excel date/time кодируется в JSON объектом с iso8601 и excel_type; числовые/текстовые значения не нормализуются. Это техническая сериализация; исходный workbook с форматом и точным XML остаётся неизменным. Вредоносные XML entities блокируются defusedxml; внешние workbook links не загружаются.

Перед openpyxl проверяются реальные workbook sheet relationships, включая нестандартные пути и расширения частей OOXML. Несогласованный тип связи отклоняется; перенос worksheet в другой ZIP entry не обходит проверку координат. XML metadata workbook/relationships ограничена 1 MB на часть. Защита от sparse XLSX не изменяет и не обрезает исходные значения: неподдерживаемый файл завершается безопасной ошибкой.

Generic XML: документ `<records>` с прямыми дочерними `<record id="…">`. ONE_C XML: синтетический профиль `<Выгрузка>` с прямыми `<Объект Тип="Справочник.Номенклатура" Ид="…">`, внутри произвольные элементы свойств. Это минимальный тестовый адаптер, не универсальный production-коннектор 1С. Реальную выгрузку пилота нужно сверить отдельно. Namespace/другой корневой профиль пока не поддерживается. Raw payload сохраняет дерево tag/attributes/text/tail/children; source_position — номер объекта и tag. Неподходящий объект — запись в errors, другие корректные объекты сохраняются. DTD/entities/external resolution запрещены, максимальная вложенность64; сломанный документ даёт FAILED и сохраняет ранее зафиксированные строки.

## Дубликаты, задачи и восстановление

Уникальность первичной загрузки: `(source_system_id, SHA-256)`. Идентичные байты для того же источника возвращают HTTP200, `duplicate=true` и metadata существующего первичного пакета; новую задачу/RawRecord не создают. Имя повторно выбранного файла не заменяет первое имя. Тот же файл у другого источника — самостоятельная загрузка с собственным provenance. Конкурентные запросы защищены уникальным индексом PostgreSQL.

Новый файл: HTTP201 после сохранения оригинала/регистрации ImportBatch; JSON показывает текущий статус (обычно QUEUED). Это подтверждение приёма, а не успешного разбора. В запросе не выполняется parsing. Если очередь недоступна, принятый пакет получает FAILED с безопасным сообщением и остаётся доступным для просмотра/повтора.

Worker слушает `forest-keeper` (FK_IMPORT_QUEUE_NAME), job identifier `import-<UUID>`, timeout FK_IMPORT_JOB_TIMEOUT=900сек. Записывает chunks по500 строк; уникальная позиция RawRecord и общий PostgreSQL advisory lock защищают повторную/параллельную доставку. Повторная доставка завершённой задачи ничего не меняет. Продолжение PROCESSING после остановки не удаляет исходные chunks и не дублирует позиции. Нормальный файл без ошибок — COMPLETED, пригодные записи плюс ошибки — COMPLETED_WITH_ERRORS, системная/структурная ошибка или отсутствие пригодных записей при ошибках — FAILED. Header-only CSV без ошибок может завершиться с0записей.

Audit: IMPORT_UPLOADED (actor uploader), IMPORT_QUEUED/PROCESSING/COMPLETED/COMPLETED_WITH_ERRORS/FAILED (system actor), SourceSystem ID и ImportBatch ID. Не пишутся полный payload/файл/пароли. Технические сообщения — JSON с event, import_batch_id и job_id, без исходных exception strings/credentials.

После сбоя работающий worker не помечает пакет COMPLETED заранее. RQ failure callback переводит QUEUED/PROCESSING в FAILED; при hard kill распознавание abandoned job зависит от RQ maintenance/job timeout. При запуске worker сверяет пакеты старше60сек: NEW снова проходит NEW→QUEUED и публикуется; QUEUED/PROCESSING с отсутствующей/завершившейся/failed задачей становятся FAILED. Тот же advisory lock и повторное чтение строки защищают от перезаписи одновременно завершившегося пакета. После восстановления БД/очереди эту операцию можно вызвать явно:

```bash
docker compose exec worker python -m app.imports.recover
```

POST `/imports/{id}/retry` с import.retry разрешён для FAILED/COMPLETED_WITH_ERRORS и создаёт **новый** ImportBatch со ссылкой retry_of_id и тем же неизменяемым оригиналом. Старые статус, RawRecord и ошибки не переиспользуются. Одновременный активный повтор того же пакета запрещён. Дубликат upload по-прежнему указывает на первичный пакет; пользователю нужно явно выбрать повтор. Попытка восстановления не использует новые/запрещённые переходы lifecycle.

FS и PostgreSQL не имеют общей транзакции. При аварии до регистрации в БД возможен невостребованный UUID-файл; API не удаляет его автоматически и не перезаписывает оригиналы. После commit NEW восстановление описано выше. Перед обновлением/переносом сохраняйте одновременно PostgreSQL и import_files; после обычного restart оба остаются. Очистка томов не является процедурой обновления.

## Проверка и capacity profile

Синтетические fixtures и ожидаемые результаты: `tests/data/import/manifest.json`. Security fixtures не содержат реальных credentials; вредоносное содержимое не исполняется. Все обязательные scripts/check*.sh и test-security-gates.sh остаются gates. Integration использует отдельные schema, файловый каталог и очередь; browser E2E создаёт два источника, импортирует CSV и 1С XML, проверяет raw/provenance, duplicate и partial errors. E2E accounts удаляются; тестовые пакеты/raw/audit остаются историческими facts в development БД.

Детерминированный генератор30атрибутов:

```bash
backend/.venv/bin/python scripts/generate-import-data.py /tmp/source-a.csv --count 100000 --seed 41
```

Допустимые counts:100,1000,10000,100000. Отдельный capacity profile не входит в быстрые unit tests. С локальными development PostgreSQL/Redis и экспортированной `.env`, из backend:

```bash
FK_TEST_INTEGRATION=1 uv run --frozen python -m tests.benchmark_import --records 100000
```

Профиль создаёт временную schema/хранилище/очередь, принимает два разных набора по100000×30, исполняет задачи через RQ и проверяет metadata p95≤1сек при10одновременных сессиях. Удаляются только собственные fixtures. Не запускать против production; никаких source write-back в подсистеме нет.
