# Forest Keeper — Stage Gate Checklist v0.1

Статус: обязательная проверка между этапами MVP.

## Цель

Не дать реализации постепенно уйти от исходного замысла Forest Keeper просто потому, что локально проходят тесты. Перед принятием каждого этапа и началом следующего выполняется отдельная проверка соответствия продуктовой идее и архитектуре.

## 1. Gate соответствия замыслу

Проверить минимум:

- Forest Keeper остаётся надстройкой над системами заказчика, а не их заменой;
- source systems остаются read-only в Prototype 0.1;
- raw и provenance не теряются и не переписываются derived-результатами;
- canonical representation не объявляется истиной;
- неизвестная истина остаётся UNKNOWN / human review;
- AI не является system of record и не получает полномочия принимать финальные бизнес-решения;
- подтверждённое решение человека остаётся первичным источником адаптации;
- новые состояния, enum, permissions и lifecycles не придумываются молча;
- модульный монолит не дробится без необходимости;
- Web Client остаётся основным MVP-клиентом, backend остаётся client-independent;
- этап не протащил функциональность следующего этапа без отдельного решения.

## 3. Gold Reference / эталон клиента

Gold Reference — это версионированный настраиваемый эталон/базовая модель клиента. Это **не абсолютная истина** и не текущее pre-match/canonical representation.

Он может изменяться в процессе эксплуатации по мере накопления подтверждённых решений людей и последующей формализации устойчивой практики.

Цепочка изменения:

`подтверждённые решения людей → выявленный устойчивый паттерн → предложение формализовать → явное подтверждение человека → новая версия Gold Reference / Rule / Customer Template`.

Запрещено:

- автоматически менять Gold Reference по одному решению;
- менять его только на основании AI confidence;
- переписывать старую версию;
- молча пересчитывать исторические результаты новой версией и показывать их так, будто они всегда были получены по новым правилам.

## 4. Что обязательно при изменении Gold Reference

Любое изменение должно иметь:

- новую версию;
- автора/подтвердившего пользователя;
- дату и время;
- причину;
- diff старого и нового эталона;
- ссылки на решения/основания, если изменение выросло из практики пользователей;
- область действия: domain/entity/attribute/rule;
- audit event;
- исторически доступную предыдущую версию.

До активации система должна выполнить impact analysis настолько, насколько позволяют текущие данные, и показать пользователю предупреждение:

> изменение эталона меняет критерии оценки и может потребовать пересмотра ранее рассчитанных результатов.

Пользователь должен видеть, что именно потенциально затрагивается: например matching, conflicts, recommendation criteria, quality checks или иные derived results.

## 5. После изменения Gold Reference

Зависимые результаты нельзя молча считать актуальными.

Для каждого зависимого результата требуется одно из двух:

1. повторная оценка по новой версии;
2. явная метка, что результат устарел / рассчитан по предыдущей версии эталона.

Исторический результат всегда должен оставаться воспроизводимым по версии правил/эталона, которая действовала на момент его получения.

Новая версия не переписывает историю человеческих решений. Если старое решение было принято в контексте старого эталона, этот контекст сохраняется.

## 6. Проверка влияния на критерии оценки

На каждом stage gate отдельно проверить:

- появились ли новые критерии/weights/thresholds/rules;
- зависят ли они от Gold Reference;
- сохранена ли версия этих критериев в derived results;
- можно ли определить, какие результаты становятся stale при изменении reference;
- есть ли механизм re-evaluation либо хотя бы безопасного stale marking до этапа, где re-evaluation будет реализован полностью.

Если текущий этап ещё не реализует CustomerTemplate/Rules, он не обязан реализовывать весь механизм изменения Gold Reference, но **не должен принимать архитектурные решения, которые сделают версионирование, impact analysis или re-evaluation невозможными позже**.

## 7. Gate качества

После архитектурной проверки действуют обычные acceptance gates:

- обязательные unit/integration/browser tests;
- security gates;
- migration validation;
- performance/capacity профиль этапа;
- независимый review/retest;
- зелёный CI на финальном SHA;
- merge;
- зелёный CI на merge commit в `main`.

Только после выполнения **архитектурного gate + технического gate** этап считается принятым.

## 8. Обязательная запись результата

Acceptance report этапа должен содержать отдельный раздел **Architecture / Product Intent Gate** с ответами:

- соответствует ли текущая реализация основному замыслу;
- какие архитектурные отклонения обнаружены;
- какие из них исправлены;
- какие явно приняты Decision Log;
- не нарушены ли raw/provenance/human-in-the-loop/AI boundaries;
- не зафиксирован ли Gold Reference как неизменяемая истина;
- сохраняется ли возможность versioning + impact analysis + stale/re-evaluation при будущих изменениях Gold Reference.

Если на любой критический пункт ответ отрицательный, этап не закрывается независимо от количества PASS-тестов.
